### P1 - The required selected-actions policy excludes the unchanged CI workflow that must pass

The plan requires CI to pass at the exact source commit before candidate dispatch (`candidate:161-163`, `candidate:2085-2087`) and later requires four exact successful CI check rows (`candidate:1754-1764`). It also requires the repository Actions policy to be `allowed_actions: selected`, with both provider-category flags false and exactly five allowed immutable action references (`candidate:1774-1798`).

The exact source write set does not include `.github/workflows/ci.yml` and expressly forbids changing the existing CI workflow (`candidate:201-224`). The authenticated baseline CI bytes at `.github/workflows/ci.yml:20-21` invoke `actions/checkout@v4` and `actions/setup-python@v5`. Those mutable references are not either of the exact allowed references `actions/checkout@34e114...` and `actions/setup-python@a309ff...`, and the policy has no GitHub-owned or verified-action category fallback.

Therefore the candidate cannot simultaneously preserve the exact twelve-path source slice, observe the required policy as `OBSERVED_MATCH`, and obtain the required CI PASS. The plan also grants no repository-policy mutation or separately reviewed policy-transition transaction that could establish which policy governed the recorded CI run. Even if an unrecorded human changed the policy after CI, the resulting CI evidence would not have run under the final bound restriction. This is both an internal gate-sequence contradiction and a supply-chain gap: the final CI evidence still executes two mutable action tags that Gate R-SOURCE-X never authenticates.

### P1 - SOURCE-W's Windows child/process and transitive runtime boundary is asserted but not bound

SOURCE-W invokes fourteen prewrite and four postwrite processes before independent source review. It requires bounded tree termination and a liveness observation (`candidate:226-243`, `candidate:270-281`, `candidate:530-578`, `candidate:731-747`) but does not name, version, hash, capability-test, or independently review a Windows process-tree supervisor. There is no Job Object, descendant enumeration, PID/start-time binding, kill-on-close containment, or task-host process capability record analogous to the detailed `NATIVE_BOUNDED_HTTPS_GET` gate. Observing the direct process terminate is not proof that a wrapper or detached descendant terminated.

The local tool identity is also not the active transitive code boundary. The plan pins only `C:\Program Files\Git\cmd\git.exe` and `...\Python313\python.exe` (`candidate:226-243`). Read-only identity checks confirmed the advertised wrapper/executable hashes, but also confirmed unbound executable runtime components: `C:\Program Files\Git\mingw64\bin\git.exe` is a separate 4,321,168-byte Git executable, and `Python313\python313.dll` is a separate 6,125,912-byte Python core. The postwrite verifier imports `argparse`, `hashlib`, `json`, `tomllib`, and `pathlib` from the unbound Python installation (`scripts/verify_release.py:6-10`). `-I -B -S` suppresses site startup; it does not bind the interpreter DLL or standard-library bytes.

Consequently a PASS `local_tools` row and a matching version line do not authenticate all code that actually runs, and the result schema can label direct-process liveness `TERMINATED` without a reviewed descendant-absence basis. These processes run before Gate R-SOURCE-X and outside the later Linux subreaper/Landlock/seccomp boundary. The source-writing gate therefore lacks the exact command/process containment that the plan claims and that release-source mutation requires.

### P2 - An authorized retained directory is missing from the SOURCE-W failure schema

The source slice may create the initially absent parent directory `docs/releases` before creating `docs/releases/v1.2.0.md` (`candidate:201-219`). On failure it promises a complete retained-state report without cleanup (`candidate:474-480`).

`source-result.json.files`, however, contains exactly the twelve source file paths plus local `toolchain/toolchain.json` (`candidate:686-699`). The repository `unexpected_paths` rows contain only observed **unexpected** entries (`candidate:700-724`). The authorized `docs/releases` directory is neither one of the file rows nor unexpected. Git status/diff also does not report an empty untracked directory.

A failure after the parent directory is created but before `v1.2.0.md` is created can therefore retain a material repository path that no result row represents. The absent file row does not prove whether its parent is absent, a regular directory, a reparse point, or another type. This contradicts the complete retained-state and recovery semantics and prevents SOURCE-X from reconstructing the exact partial filesystem state from durable evidence.

## Required revisions

1. Make the CI workflow and final selected-actions policy mutually executable and independently bound. The exact reviewed source write set must include any required CI pin changes, and CI evidence must prove the owner-approved policy in effect for that run rather than rely on an unrecorded provider-policy transition.
2. Freeze and independently review one concrete Windows process-tree/liveness mechanism before SOURCE-W execution. Bind the actual Git/Python transitive runtime used, not only launcher executables/version output, and make success/timeout/overflow descendant-absence claims mechanically supportable.
3. Add every authorized directory, including `docs/releases`, to a total before/after/retained-state schema with presence/type/reparse/identity rules for success and every partial failure. Do not hide an authorized empty directory from both expected and unexpected inventories.
