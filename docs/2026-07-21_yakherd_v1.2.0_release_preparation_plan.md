## 3. Blocking pipeline defect and selected repair

The present `.github/workflows/publish.yml` starts only after a public tag is
pushed. It builds the wheel and sdist and automatically hands them to the OIDC
PyPI job. That ordering cannot satisfy the governing Gate R contract: the
exact completed artifact bytes, their inventories, and their smoke evidence
must exist before the one final Sol Ultra review and before the owner gives a
fresh publication instruction.

The presence of a GitHub environment named `pypi` does not prove that a human
approval rule is configured. Local builds also cannot stand in for different
bytes rebuilt later by GitHub Actions. The current workflow is therefore not a
permitted v1.2.0 publication path.

The selected repair separates release into two workflows:

1. a manually dispatched, unprivileged candidate workflow builds and retains
   exact artifacts from one exact `main` commit without creating a tag or
   publishing anything;
2. after the exact artifacts receive the final Ultra PASS and the owner sees
   their identities and explicitly authorizes publication, an independently
   dispatched publication workflow retrieves those same candidate bytes,
   verifies their frozen identities, publishes them to PyPI through OIDC, and
   then creates the GitHub release with the same files.

There is no rebuild after final review. Publication is a monotonic transaction,
not an atomic cross-provider claim; partial states are handled by the stop and
recovery rules in Section 11.

## 11. Failure, partial publication, and rollback

Before the source commit is pushed, a failure is local: stop, preserve exact
source/evidence, make no cleanup or retry, and obtain a newly reviewed candidate
or recovery plan. After the source commit is pushed but before the tag, the
reviewed release plumbing is public but no v1.2.0 tag or distribution is
public; stop, preserve that honest commit and evidence, and do not rewrite
history to make the candidate appear clean.

After the tag is pushed, it is immutable. It is never moved, deleted, recreated,
or force-pushed. A publication-dispatch failure before PyPI upload leaves a
public tag but no release claim; stop and record exact remote state. A same-byte
workflow rerun is not automatic and requires a reviewed recovery decision.

PyPI filenames and versions are immutable. Any partial or complete PyPI upload
is a release incident boundary: stop, preserve the run and provider responses,
observe which exact files are public, and request explicit owner remediation.
Do not overwrite, delete, or silently substitute an artifact. A yank or
successor `1.2.1` is a separately reviewed owner decision, not rollback by this
plan.

A readable PyPI version with exactly one of the two exact expected files and no
other file is
`TAG_AND_PARTIAL_PYPI`. A readable version/file observation that differs in
filename, count other than that proper subset, bytes, hash, requires-Python, or
other closed immutable-version metadata is
`TAG_AND_NONCONFORMING_PYPI`; its 090 reason is
`NONCONFORMING_PYPI`. Zero visible files after an upload reports success is
also nonconforming rather than guessed absent. This state takes precedence
regardless of whether the simultaneously observed GitHub state is absent,
draft, public, nonconforming, or UNKNOWN; the provider rows retain that exact
secondary observation. Neither state permits retry.

The GitHub release job runs only after PyPI success. It first creates a
nonpublic draft, attaches and verifies both exact assets, and only then makes it
public. Failure before draft creation leaves `TAG_AND_COMPLETE_PYPI`; failure
with a retained incomplete or complete draft leaves respectively
`TAG_AND_COMPLETE_PYPI_WITH_INCOMPLETE_GITHUB_DRAFT` or
`TAG_AND_COMPLETE_PYPI_WITH_COMPLETE_GITHUB_DRAFT`. A draft is not called a
public release and is never automatically deleted, overwritten, finalized, or
retried. A separately reviewed GitHub-only recovery may inspect the exact draft

it must not invoke PyPI. After the draft-to-public call, timeout or ambiguity
